# nurseApp — Design Decisions (OOD)

Lightweight Architecture Decision Records for the Phase 1 object-oriented design. Each
record states the decision, the context, and the rationale. These complement
`docs/architecture.md` (the standing rules) by capturing the *choices* made during OOD and
why. Referenced from US006.

Adapted from the Nortada project's ADR style — decisions below are specific to nurseApp's
own domain (devices, shifts, checklists), not carried over verbatim.

---

## ADR-001 — Scheduled job for device maintenance warnings

**Decision.** Maintenance due-date warnings are generated by a **scheduled background job**
(`MaintenanceWarningScheduler`, daily) that sweeps every `Device` and evaluates its
`Periodicity` against `lastReplacedAt`. Read endpoints (`GET /api/devices`,
`GET /api/devices/{id}`) still compute `MaintenanceStatus` live on request (it's a cheap
pure date calculation — see ADR-005) — the scheduler's job is specifically to *push*
warnings ahead of time (e.g. onto a nurse's or admin's dashboard) rather than only surfacing
staleness when someone happens to open that device's screen.

**Context.** Device replacement cadence changes on the order of days or weeks, not seconds.
A nurse starting a shift needs to know *before* checking a device whether something is
already due or coming due soon — waiting for an on-demand read the moment they open the
checklist is too late to plan around.

**Rationale.**
- **Proactive, not reactive** — warnings need to exist before anyone asks; a daily sweep is
  what makes a "devices due this week" view or notification possible at all.
- **Bounded, predictable load** — one daily pass over all devices instead of recomputing
  warning state under every request.
- **Fit to the data** — replacement cadence is measured in days, so daily granularity is
  more than sufficient.

**Trade-off / rejected alternative.** Pure on-demand computation (no scheduler) is simpler
and always accurate for a single device read, but can't proactively surface "devices due
soon" without a full scan — and that scan is exactly what the scheduler already does once a
day. The two are complementary, not redundant: live computation for accuracy, the scheduler
for proactive visibility.

## ADR-002 — REST Level 3 (HATEOAS) with HAL+JSON

**Decision.** The API is hypermedia-driven (Richardson Maturity Level 3) using the
`application/hal+json` representation. Every resource includes a `_links` section; the
collection includes pagination links (`first`/`prev`/`next`/`last`) and each item includes
`self`/`collection`.

**Context.** nurseApp is an internal hospital tool, not a public multi-client API — but
we're deliberately keeping architectural parity with how Nortada is built, since both
projects follow the same standing conventions (`architecture.md`).

**Rationale.**
- **Discoverability & decoupling** — any future client (web dashboard, companion mobile app)
  navigates by following links rather than hard-coding URI templates.
- **Standard pagination** — HAL's page metadata + navigation links are a well-understood
  convention that Spring HATEOAS supports directly.
- **Consistency across projects** — one architectural style to reason about instead of two.

**Trade-off.** HAL adds envelope verbosity versus a flat JSON body, and is arguably more
than a single-client internal tool strictly needs. Accepted for consistency with the
established project style and to keep the door open for additional clients later.

## ADR-003 — Three-model separation (domain / data model / DTO)

**Decision.** Three distinct types per concept, mapped explicitly at boundaries: the pure
`domain` object (e.g. `Device`), the JPA `@Entity` data model
(`infrastructure/persistence/datamodel/DeviceDataModel`), and the HAL+JSON `web/dto`
(`DeviceResponse`). Dedicated mapper classes translate between them.

**Rationale.**
- **Protected Variations / Low Coupling** — ORM shape and wire shape can change without
  touching business rules; the domain has zero framework knowledge (`architecture.md`
  section 3.1).
- **Single Responsibility** — no class serves two layers; mappers (Pure Fabrication) own
  the translation and are independently testable.

**Trade-off.** More classes and explicit mapping code versus reusing one annotated class
everywhere. Accepted — sharing a class across layers is the recurring Clean/Onion
Architecture defect this project explicitly avoids.

## ADR-004 — Ports & Adapters (Dependency Inversion)

**Decision.** The `application` layer depends only on outbound **ports**
(`DeviceRepositoryPort`, `ShiftRepositoryPort`, `ChecklistExecutionRepositoryPort`,
`MaintenanceReportRepositoryPort`, `UserRepositoryPort`, `OperatingRoomRepositoryPort` —
interfaces in `domain/repository`). Concrete adapters in `infrastructure` implement them
(e.g. `DeviceRepositoryAdapter` over Spring Data JPA). Wiring happens once in
`infrastructure/config/AppConfig`.

**Rationale.** Keeps dependencies pointing inward (DIP); lets persistence technology change
(e.g. swapping the JPA adapter) without editing use cases; enables mocking ports in unit
tests, matching the TDD conventions already in use for `Periodicity`.

## ADR-005 — Maintenance due-date detection as a Strategy behind a domain service

**Decision.** Due-date detection logic lives in the `domain` layer as a
`MaintenanceDueService` delegating to a `MaintenanceDueStrategy` (default
`PeriodicityBasedDueStrategy`, wrapping the `Periodicity.nextDueDateFrom(...)` rule already
built and tested). It takes a `Device` and a reference date, and returns a
`MaintenanceStatus` (`OK` / `DUE_SOON` / `OVERDUE`).

**Rationale.**
- **Information Expert / SRP** — the rule is one cohesive responsibility, separate from
  scheduling (ADR-001) and from HTTP concerns.
- **Open/Closed via Strategy (GoF)** — an alternate rule (e.g. usage-count-based instead of
  calendar-based) swaps in without editing callers.
- **Testability** — a pure function `(device, today) -> status` is directly unit-testable at
  boundary values, the same way `PeriodicityTest` already covers `Periodicity`'s boundaries.

## ADR-006 — Use cases as Facades

**Decision.** Client-facing operations are single-method application services
(`GetDeviceListUseCase`, `StartShiftUseCase`, `RunChecklistUseCase`,
`RecordDeviceReplacementUseCase`, `ReportMaintenanceIssueUseCase`) that coordinate ports and
the domain services behind one call.

**Rationale.** Controllers stay thin GRASP Controllers (pure HTTP↔use-case translation); the
Facade hides the multi-collaborator orchestration; each use case has one reason to change.

## GoF patterns used (summary)

| Pattern | Where | Purpose |
|---|---|---|
| Strategy | `MaintenanceDueStrategy` | Pluggable due-date detection rules (ADR-005). |
| Adapter | Repository adapters, mappers | Bridge ORM to ports (ADR-004, ADR-003). |
| Repository | `*RepositoryPort` + JPA adapter | Persistence hidden behind a port. |
| Facade | `*UseCase` classes | One coordinating method per operation (ADR-006). |
| Factory | value-object constructors / `DeviceId.newId()` | Enforce invariants and generate identity at construction. |

## Design-only types pending scaffolding

The domain model introduces types that do **not** exist in `domain/` yet and are design
blueprints to be created during backend scaffolding:

- Identity value objects: `DeviceId`, `RoomId`, `ShiftId`, `ChecklistId`, `ReportId`, `UserId`.
- Other value objects: `Role`, `DeviceType`, `ShiftWindow`, `ShiftStatus`, `CheckStatus`,
  `ReportStatus`.
- Entities / aggregate roots: `Device`, `User`, `OperatingRoom`, `Shift`,
  `ChecklistExecution` (+ `CheckItem` entity), `MaintenanceReport`.
- Domain service/strategy: `MaintenanceDueService`, `MaintenanceDueStrategy`,
  `PeriodicityBasedDueStrategy`.
- Application: all `*UseCase`, `*Port` interfaces.
- Infrastructure: JPA data models, mappers, repository adapters, `MaintenanceWarningScheduler`.
- Web: controllers, DTOs, mappers.

Today `domain/` contains only `Periodicity` (built via TDD, see
`PeriodicityTest`).
